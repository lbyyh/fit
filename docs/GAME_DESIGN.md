## 附录：评估口径说明

我给每个构思打分时用的标准，先摆出来免得你觉得我瞎评：

**可行性**（能不能做出来）
- 技术风险：有没有我拿不准的技术点，要不要先做验证
- 依赖：需不需要外部服务、付费资产、额外原生库
- 工程量：以"人天"估算，含代码 + 配表 + 调试

**拓展性**（值不值得做）
- 内容弹性：做完是"一次性的"，还是能持续长出内容
- 复用度：这个系统能支撑多少后续玩法
- 耦合度：改动它会不会牵动一大片

**方案给出方式**
- 优先复用 §3.1 已有基座
- 明确数据流向：谁权威、谁同步、谁存盘
- 标注需要新建的脚本与大致结构
- 凡是涉及网络同步的，一律说明服务器权威边界（防止作弊点错地方）

**我会主动反对的情况**
- 单人做不完的规模
- 会让存档结构推倒重来的设计（越早说越好）
- 与 Listen Server 拓扑冲突的玩法（比如要求强反作弊的竞技排行）
