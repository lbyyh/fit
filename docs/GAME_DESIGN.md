### 一句话描述

```
（第一人称、地牢闯关、武器（枪械/刀/等脑洞爆炸的武器系统）、弹幕射击游戏、Q版像素FPS、轻松欢乐的多人联机、没有 PVP 对抗压力。亮点不在于严谨配合，而在于整活）
```

### 六个必须先回答的问题

不用一次答完，能答几个答几个，剩下的留着也行。

| # | 问题 | 你的答案 |
|---|---|---|
| 1 | **这是个什么游戏？** 用一句话向朋友安利会怎么说？ |轻松欢乐的多人联机合作地牢闯关fps游戏 |
| 2 | **几个人玩？** 单人、2 人、4 人 co-op、还是 8+ 人大乱斗？ | 暂定1-5人|
| 3 | **核心动词是什么？** 玩家 80% 时间在做的那个动作（钓 / 打 / 造 / 开 / 偷 / 跑） |打/射击 |
| 4 | **一局多长？** 5 分钟一局的肉鸽式，还是无限存续的存档式？ |闯关模式(暂定丛林、海岛、火山等经典场景，每图分n个小房间+boss房) |
| 5 | **卖给谁？** 谁会为它掏钱，他们在玩什么别的游戏？ | 喜好联机合作的休闲游戏玩家|
| 6 | **你和同类游戏的差异在哪？** 凭什么玩家选你不选别的？ | 独特丰富的游戏思路和玩法|

### 玩家体验分层

| 时间尺度 | 玩家在做什么 | 应该感到 |
|---|---|---|
| **30 秒** | 进第一个房间、开枪、怪炸成卡通碎片 | "哦，手感不错"，5 秒内懂规则 |
| **5 分钟** | 清掉 2-3 个房间，摸到第一把脑洞武器 | 好奇下一把能开出什么鬼东西 |
| **1 小时** | 打完一整条关卡线，干掉一个 Boss | "再来一局" / "叫上朋友一起" |
| **10 小时+** | 解锁武器与皮肤，和朋友开发整活套路 | 有聊资，愿意带新人入坑 |

## §2 核心循环

```text
局内（单局 20-40 分钟）

  [ 出发 ] → [ 战斗房：清怪 → 开门 ] ⇄ [ 走廊分支：选路 ]
                        │
                        ├→ [ 宝箱房 ]  开一把新武器
                        ├→ [ 商店房 ]  用局内货币买道具
                        ├→ [ 抽奖房 ]  赌一把，可能血赚可能暴毙
                        └→ [ 精英房 ]  高风险高回报
                        │
                        ↓
              [ Boss 房 ] → [ 结算 ]

局外（永久保留）

  [ 结算货币 / 解锁武器 · 角色 · 皮肤 ] → [ 下一局起点 ]
                        ↓
                     回到出发
```

**双循环的关键**：局内随机（每局体验不同）+ 局外累积（每次都不白打）。
局外累积给长线动力，局内随机保证第 100 局仍有新鲜感。

### 5.1 三个必须先解决的冲突

这三条不定，后面做多少都可能在白干。**优先级高于任何单条构思。**

#### 冲突一：第一人称 vs 弹幕地狱（设计核心风险）

**问题**：2D 弹幕游戏（东方、以撒）成立的前提是**玩家能看到全屏所有子弹**。
第一人称 FOV 只有 90-110°，背后 270° 完全看不见。把满屏弹幕塞进第一人称，
玩家体感不是「惊险地躲」，而是「莫名其妙地死」—— 这两者之间只隔着一个可读性。

**你的 ID-009（屏幕边缘红光提示侧面/背后威胁）方向完全正确**，说明直觉是对的。
但光靠提示还不够，需要四件事配套：

1. 敌人**优先生成在玩家正面扇形**（±120°），背后的敌人用音效+红光预警，不要直接放冷枪
2. **降低弹速、增大弹体** —— 慢速大弹丸在第一人称下可读性远好于快速小弹丸
3. 同屏敌人**控制在 5-8 个**，弹幕总数有上限
4. 子弹用**自发光材质 + 拖尾**，在暗色地牢里极度醒目

**我的建议**：把「弹幕」定位成 **Ultrakill 式可预判的投射物模式**（有节奏、能读招、
能反击），而不是东方 Project 式的满屏弹幕雨。前者在第一人称下成立，后者不成立。
这不影响「脑洞武器」和「爽感」，只是把难度建立在**读招**而不是**躲密度**上。

#### 冲突二：第一人称 + 皮肤系统（商业矛盾）

**问题**：ID-003 说「皮肤永久保留」，但**第一人称看不见自己的角色**。
休闲联机游戏的长线动力和商业化很大程度上靠外观收集，第一人称会把这块价值砍掉大半。

四个解法，需要你选（§6-Q2）：

| 方案 | 效果 | 代价 |
|---|---|---|
| 手部 + 武器模型可见 | 皮肤体现在手套/武器上，保留 FPS 纯粹感 | 展示面积小 |
| 大厅 / 结算 / 死亡时展示全身 | 有展示场景，不影响战斗 | 战斗中看不见，社交展示弱 |
| 加观战 / 回放视角 | 死亡后能看队友，顺便强化「整活」 | 额外工作量 |
| 改第三人称 | 皮肤价值最大化，萌系造型能看见 | 不是 FPS 了，瞄准手感要重做 |

#### 冲突三：房主即服务器 + 弹幕精度（技术）

**问题**：Listen Server 下房主 0 ping，其他 4 人 100ms+。
密集弹幕对延迟极敏感——100ms 延迟在弹幕里就是生与死。

**但这是 PVE 合作，不竞技，所以不公平是可接受的。** 真正要解决的是
**「我明明躲开了却被判中」** 这个体感问题。

**技术方案**（业界标准做法）：

- **位置**：客户端预测 + 服务器回滚。FishNet 4 内建 Prediction / Reconciliation，现成的
- **弹幕表现**：客户端本地插值渲染，视觉流畅
- **伤害判定**：服务器权威，且**碰撞判定加宽容度**（胶囊体 + 少量宽容量），
  让「擦边」判定为躲开而非命中
- **翻滚无敌帧**：必须服务器权威，否则客户端可被改成永久无敌（见 ID-010）

一句话原则：**躲避的体感放客户端，生死的结果放服务器。**

### 5.2 分组详细评估

#### 组 1：关卡结构（ID-001 / ID-005）

**ID-005 房间图 + 特殊房** — ✅ 采纳，这是整个游戏的骨架

- 拓展性 **极高**：房间是可以无限堆的内容单元。新武器、新敌人、新机制
  都能以「新房间模板」的形式加进来，不用动核心代码。这是这个设计最大的资产。
- 技术方案：
  - 房间做成 Prefab，带**锚点（门位）**标记
  - 生成器维护一张房间图，按规则连接（战斗房为主干，特殊房挂分支）
  - 特殊房类型（宝箱/商店/抽奖/精英/Boss）用同一套接口 `IRoomBehaviour`，
    新增特殊房只需加一个实现类
  - 复用 `IslandStreamer` 改成的 `RoomStreamer` 做加载调度
- 成本：4-6 天
- 风险：**门位对齐**是这类系统最常见的坑，房间 Prefab 必须严格遵守锚点规范

**ID-001 高低差 / 平台** — ⏸ 暂缓

- 与弹幕有冲突：高低差会让玩家的空间判断变复杂，叠加第一人称和弹幕，
  容易出现「不知道子弹从哪个高度飞过来」
- 建议：**保留，但克制** —— 固定两种高度（地面 / 一层平台），平台边缘做视觉高亮，
  不做立体迷宫
- 等 ID-005 和射击手感跑通后再加

#### 组 2：可读性三件套（ID-007 / ID-008 / ID-009）— ✅ 全部采纳，且**优先做**

这是整份构思里**性价比最高**的三条。成本低（合计 2-3 天），
但直接决定「弹幕 FPS」这个组合能不能成立。

- ID-007 发光轮廓 + 预警光效：子弹用不受光的自发光材质 + 拖尾
- ID-008 发射前摇：**前摇时间建议 0.3-0.5 秒**，太短读不到，太长拖沓。
  前摇期间敌人身上加充能光效，这是给玩家的「读招窗口」
- ID-009 屏幕边缘提示：按威胁方向在屏幕对应边缘渲染红色渐变，
  配 3D 音效定位。背后威胁用更明显的脉动提示

**建议顺序**：先做这三件，再做敌人 AI。否则调 AI 时无从判断「难」是因为设计还是因为看不清。

#### 组 3：操作手感（ID-010 / ID-011）

**ID-010 翻滚闪避** — ✅ 采纳

- 必须有**无敌帧（i-frame）**，建议 0.3 秒左右，配合 0.5 秒冷却
- 无敌帧**必须服务器权威**：客户端只发「我按了翻滚」，服务器判定是否在无敌状态。
  否则客户端改内存就能永久无敌 —— 虽然 PVE 无所谓，但会毁掉联机体验
- 成本：2-3 天

**ID-011 射击手感** — ✅ 采纳

- **后坐力只做客户端视觉**：枪口上跳、屏幕震动、准星扩散都在本地算。
  如果后坐力走服务器同步，手感会立刻崩掉
- **辅助瞄准大方做**：PVE 没有公平性问题，玩家爽就是对的。
  建议做「准星附近轻微吸附 + 子弹轻微追踪」，并**在设置里给开关**
- 成本：3-4 天

#### 组 4：元进度与存档（ID-002 / ID-003）

**ID-002「房主创建存档后，玩家可以加入到房主联机大厅」** — 🔬 语义需要澄清

这句话有两种读法，差别很大：

| 读法 | 含义 | 问题 |
|---|---|---|
| A. 进度绑房主存档 | 客人玩的是房主的存档 | 客人换个房主就没进度，体验割裂，且房主可篡改他人进度 |
| B. 进度跟账号走 | 客人加入房主的局，但用自己的解锁/皮肤 | 无上述问题 |

**强烈建议 B**。这是所有合作 roguelike（雨中冒险 2、GTFO）的标准做法，
也和你的 ID-003「个人局外角色永久保留」一致。见 §6-Q3。

**ID-003 局外角色 / 皮肤** — ✅ 采纳（但受冲突二制约）

- 拓展性 **极高**：这是长线动力的发动机，也是后续更新的内容载体
- 现有 `SaveData` 的「玩家进度 / 世界状态分离」设计**正好对口**：
  - 玩家进度 = 局外解锁（永久，跟账号）
  - 世界状态 = 局内进度（一局结束即弃）
- 成本：3-5 天

#### 组 5：基调（ID-004 / ID-006）

**ID-004「重点是互相整活，而非严谨战术配合」** — ✅ 采纳，**但我建议提级**

这是整份设计里最有价值的一条，也是「凭什么玩家选你不选别人」的真正答案。
但**当前重视度不够** —— 现在它只是个基调描述，没有对应的系统。

**「整活」不能只靠美术风格和语音，必须有机制支撑。** 否则玩家玩三局就没得玩了。
建议把它提为独立系统，方向参考：

- **友军互动**：可以把队友推走、可以误伤（低伤害）、可以把队友举起来当武器扔
- **滑稽死亡**：被自己的爆炸弹炸飞、被队友推下平台、被弹幕打进抽奖机
- **环境陷阱**：本来用来打怪的机关，能把队友一起送走
- **语音联动**：喊得越大声，武器威力越高（自研语音系统能直接做，这是独门优势）

最后一条别人抄不了 —— 你的语音链路是自己写的，能拿到音频能量值。
「对着麦克风吼一嗓子放大招」这种机制，商业引擎方案很难做。

- 拓展性 **极高**，成本 4-6 天（起步版）

**ID-006 萌系造型 + 轻死亡惩罚** — ✅ 采纳，与整活基调一致

- 死亡惩罚「轻」的具体程度待定，见 §6-Q4
- 成本：1 天（主要是规则，不是代码）

## §6 待你拍板

> 口味层面的问题我不替你决定。但下面这五条**每条都会影响后续工作量和返工风险**，
> 建议一次性想清楚。Q1 和 Q2 尤其重要 —— 它们决定了美术怎么投入。

### Q1.「Q 版像素」具体是哪种？

「像素」在第一人称下有两种完全不同的做法，选错要重做美术管线。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 低分辨率 3D**（推荐） | 低多边形模型 + 低分辨率纹理 + 渲染到 640×360 再放大 | 视角旋转正确、前摇动画自然（ID-008 需要）、美术成本低、有成功案例（Ultrakill / Dusk / Amid Evil） | 严格说不是「像素」，是复古 3D |
| B. 纯 Sprite 像素 | 敌人是 2D 像素图，billboard 朝向相机 | 像素味最纯 | 第一人称近距离会糊；侧面/背面要多画几套；**前摇动画要逐帧画** |

**我推荐 A。** 关键理由是 ID-008（发射前摇）—— 3D 骨骼动画做前摇很自然，
纯 sprite 要逐帧绘制，工作量翻几倍。视觉上 640×360 放大的复古 3D 和「Q 版像素」
在观感上非常接近，玩家分不清也不在意。

> 附带影响：像素风需要低分辨率 RenderTexture + 点采样放大，
> 现有三档 URP 高保真画质配置要整个重做（见 §3.1-C）。

### Q2. 第一人称还是第三人称？

见 §5.1 冲突二。第一人称看不见角色，会砍掉皮肤系统的大半价值（ID-003）。

- 坚持**第一人称**：需要接受皮肤价值打折，用「手部/武器模型 + 大厅展示 + 观战视角」补
- 改**第三人称**：皮肤价值最大化，萌系造型能看见，但瞄准手感要重做，且失去 FPS 沉浸感
- 折中：**第一人称 + 局部可见**（看得到自己的手、武器、脚），这是很多 FPS 的做法

### Q3. 存档跟谁走？

见 §5.2 ID-002。建议**跟玩家账号走，不跟房主存档走**。
需要你确认，这会决定存档结构 —— 越晚改越痛。

### Q4. 死亡惩罚「轻」到什么程度？

| 方案 | 规则 | 感觉 |
|---|---|---|
| A. 倒地可救（推荐） | 单人倒地队友可扶，全队倒地才重开整局 | 保留 roguelike 紧张感，但不惩罚个人失误 |
| B. 房间重开 | 死了重打当前房间 | 最轻松，但紧张感弱 |
| C. 整局重开 | 死了从头来 | 硬核，与「轻松欢乐」基调冲突 |

我推荐 A —— 它是「轻松」和「有压力」之间最好的平衡点，
而且**倒地待救本身就是整活素材**（队友为了救你反而团灭）。

### Q5. 现有海洋世界代码怎么处理？

Gerstner 波、水下控制器、岛屿流式（见 §3.1-C）。

- 建议：**挪到 `Legacy/` 目录保留，主工程不引用**。以后做别的题材能捡回来
- 需要你确认要不要直接删

## 附录：评估口径说明

我给每个构思打分时用的标准，先摆出来免得你觉得我瞎评：

**可行性**（能不能做出来）
- 技术风险：有没有我拿不准的技术点，要不要先做验证
- 依赖：需不需要外部服务、付费资产、额外原生库
- 工程量：以"人天"估算，含代码 + 配表 + 调试

**拓展性**（值不值得做）
- 内容弹性：做完是"一次性的"，还是能持续长出内容
- 复用度：这个系统能支撑多少后续玩法
- 耦合度：改动它会不会牵动一大片

**方案给出方式**
- 优先复用 §3.1 已有基座
- 明确数据流向：谁权威、谁同步、谁存盘
- 标注需要新建的脚本与大致结构
- 凡是涉及网络同步的，一律说明服务器权威边界（防止作弊点错地方）

**我会主动反对的情况**
- 单人做不完的规模
- 会让存档结构推倒重来的设计（越早说越好）
- 与 Listen Server 拓扑冲突的玩法（比如要求强反作弊的竞技排行）
